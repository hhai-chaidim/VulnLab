## Overview

**VulnLab** is a personal cybersecurity lab designed to explore the vulnerability research and exploitation workflow in a controlled environment.

The project focuses on identifying publicly disclosed vulnerabilities, understanding their technical details, analyzing their severity, and reproducing their behavior using intentionally vulnerable applications or isolated virtual machines.

The research process includes examining CVE records, reviewing the National Vulnerability Database (NVD), interpreting CVSS scores and vectors, analyzing public proof-of-concept (PoC) code, and inspecting HTTP requests and responses.

The project also aims to develop a lightweight Python-based tool, **CVE Lab Notebook**, to organize vulnerability research, testing evidence, and technical reports.

All practical testing is performed exclusively against systems owned by the author or explicitly authorized for testing.

## Objectives

The primary objectives of this project are:

* Understand the vulnerability research lifecycle, from CVE discovery to remediation validation.
* Learn how to interpret CVE records, NVD entries, CVSS scores, and vendor security advisories.
* Identify affected products, vulnerable versions, prerequisites, and potential security impacts.
* Analyze publicly available PoC code and understand its underlying mechanisms.
* Build and maintain an isolated vulnerable lab using Docker and/or virtual machines.
* Inspect HTTP requests and responses to understand application behavior and potential security weaknesses.
* Reproduce vulnerability behavior in a controlled environment.
* Compare vulnerable and patched versions whenever feasible.
* Develop a Python CLI tool for organizing CVE records, test cases, and evidence.
* Produce clear, reproducible technical reports suitable for a cybersecurity portfolio.

## Key Features

### 1. Vulnerable Lab Environment

* Deploy intentionally vulnerable web applications.
* Use Docker containers and virtual machines to create isolated testing environments.
* Keep vulnerable services restricted to the intended lab interfaces.
* Document setup, configuration, and cleanup procedures.

### 2. CVE Research

For each selected vulnerability, document:

* CVE identifier and official description.
* Affected products and versions.
* Vulnerability classification.
* Attack prerequisites and relevant conditions.
* CVSS version, score, vector, and scoring source.
* Vendor advisories and remediation information.
* References to public technical analyses and PoCs.

### 3. Proof-of-Concept Analysis

* Review PoC source code before execution.
* Identify dependencies, inputs, and execution flow.
* Understand the mechanism that triggers the vulnerability.
* Determine expected behavior and observable evidence.
* Document safety considerations and limitations.

### 4. HTTP Request/Response Analysis

* Capture HTTP traffic generated by lab exercises.
* Examine methods, URLs, headers, cookies, parameters, and request bodies.
* Analyze response status codes, headers, and response bodies.
* Understand how client-controlled input is processed by the application.
* Record relevant evidence for vulnerability reports.

### 5. Remediation and Validation

* Identify vendor-recommended fixes and mitigations.
* Compare behavior before and after remediation.
* Record test results and supporting evidence.
* Document residual risks and limitations.

### 6. CVE Lab Notebook

A lightweight Python CLI application intended to:

* Store CVE research records in JSON.
* Track test cases and their results.
* Organize evidence metadata.
* Calculate SHA-256 hashes of evidence files.
* Generate structured Markdown reports.

## Getting Started

### Prerequisites

Before setting up the lab, install:

* [Git](https://git-scm.com/)
* [Docker Desktop](https://www.docker.com/products/docker-desktop/)
* [Python 3](https://www.python.org/downloads/)
* [Burp Suite Community Edition](https://portswigger.net/burp/communitydownload)

VirtualBox or VMware may be installed if a dedicated Kali Linux VM or a separate vulnerable target VM is required.

### 1. Clone the Repository

```bash
git clone https://github.com/hhai-chaidim/VulnLab.git
cd VunlnLab
```

Replace `hhai-chaidim` with your GitHub username.

### 2. Start OWASP Juice Shop

Ensure Docker Desktop is running.

Pull the official Juice Shop image:

```powershell
docker pull bkimminich/juice-shop
```

Start the container with the application bound to the host's loopback interface:

```powershell
docker run --rm --name vulnlab-juice-shop -p 127.0.0.1:3000:3000 bkimminich/juice-shop
```

Open the application:

```text
http://127.0.0.1:3000
```

Verify that the container is running:

```powershell
docker ps
```

To stop the application, press `Ctrl+C` in the terminal running the container.

The `--rm` option removes the container after it stops. The downloaded image remains available locally.

### 3. Verify the Lab

Confirm that:

* The application loads successfully.
* The container is running as expected.
* The application port is bound to `127.0.0.1`.
* No vulnerable service has been intentionally exposed to the public Internet.
* The lab can be stopped and restarted successfully.

### 4. Configure Burp Suite

1. Launch Burp Suite Community Edition.
2. Configure a local proxy listener.
3. Set the browser proxy to the listener address and port.
4. Browse the local lab application.
5. Inspect HTTP requests and responses.
6. Save sanitized examples for documentation.

Do not include session cookies, authentication tokens, or other secrets in published evidence.

For additional targets, follow the setup instructions documented in the corresponding lab directory.

## CVE Research Methodology

Each vulnerability will be investigated using a consistent workflow.

### Step 1 — Identify the Vulnerability

Find a suitable CVE using trusted vulnerability databases, vendor advisories, and technical references.

### Step 2 — Verify Affected Versions

Identify the affected product, vulnerable versions, fixed versions, and relevant configuration requirements.

### Step 3 — Analyze CVSS

Record:

* CVSS version.
* Base score and vector.
* Scoring source.
* Attack Vector (AV).
* Attack Complexity (AC).
* Privileges Required (PR).
* User Interaction (UI).
* Scope or subsequent-system impact metrics, where applicable.
* Confidentiality, Integrity, and Availability impacts.

CVSS severity is not a complete assessment of risk in a specific environment. Environmental context and exposure must also be considered.

### Step 4 — Review the Vendor Advisory

Read the official advisory to understand the root cause, affected configurations, remediation, and any known limitations.

### Step 5 — Analyze the PoC

Inspect the source code, dependencies, input parameters, and expected behavior before executing anything.

### Step 6 — Reproduce the Vulnerability

Use only the isolated target configured for the selected CVE.

Record the environment, steps, observations, and supporting evidence.

### Step 7 — Validate Remediation

Where feasible, repeat the test against a patched version or apply the recommended mitigation.

### Step 8 — Write the Report

Document the findings, impact, evidence, remediation, and limitations.

## HTTP Traffic Analysis

HTTP traffic analysis is used to understand the interaction between a client and the target application.

For each relevant test, record:

| Field            | Description                       |
| ---------------- | --------------------------------- |
| Test ID          | Unique test case identifier       |
| Target Version   | Exact application version         |
| HTTP Method      | GET, POST, PUT, etc.              |
| Endpoint         | Requested path                    |
| Parameters       | Relevant query or body parameters |
| Request Headers  | Relevant HTTP headers             |
| Response Status  | HTTP status code                  |
| Response Headers | Relevant response metadata        |
| Response Body    | Sanitized response content        |
| Observation      | Actual behavior                   |
| Conclusion       | Evidence-based result             |

Example of a sanitized request:

```http
GET /example?query=test HTTP/1.1
Host: 127.0.0.1:3000
Accept: application/json
```

This is an illustrative example, not evidence of a real vulnerability.

Each analysis should distinguish observed behavior from hypotheses. A status code alone is not sufficient to prove that a vulnerability exists or has been successfully exploited.

## PoC Analysis

Public proof-of-concept code is treated as untrusted input until reviewed.

The analysis covers:

* Original source and repository.
* Commit or release identifier, where available.
* Dependencies and installation requirements.
* Input parameters and execution flow.
* Target product and version requirements.
* Relevant requests or operations.
* Expected output and success conditions.
* Potential destructive or unintended behavior.
* Limitations and reproducibility.

PoCs are tested only in an authorized, isolated environment. Third-party code is not assumed to be safe simply because it is publicly available.

## Security and Ethical Considerations

This project is intended for cybersecurity education and authorized security testing.

* All exploitation is restricted to systems owned by the author or explicitly authorized for testing.
* Vulnerable applications are kept within the intended isolated lab environment.
* Public PoC code is reviewed before execution.
* No real user data, credentials, or session tokens are intentionally collected.
* Sensitive information is removed from screenshots, logs, and HTTP captures before publication.
* Vulnerability findings are documented responsibly.
* Third-party tools, source code, and datasets remain subject to their respective licenses.

**Do not use the techniques or configurations described in this repository against systems without explicit authorization.**
